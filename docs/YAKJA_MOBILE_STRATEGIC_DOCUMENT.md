# سند راهبردی فاز دوم — اپلیکیشن اندروید «یکجا» (YAKJA Mobile)

**نسخه سند:** ۲.۰ (بازبینی‌شده و نهایی)
**تاریخ:** ۳۰ سرطان ۱۴۰۵ (۲۱ ژوئیه ۲۰۲۶)
**مرجع بالادستی:** `YAKJA_STRATEGIC_DOCUMENT.md` (وب)، بند ۱۳.
**نقش این سند:** مرجع فنی نهایی و کامل معماری فاز دوم. هر تصمیم معماری این پروژه همین‌جا گرفته و مستند شده — چیزی برای تصمیم‌گیری بیشتر باقی نمانده است.

---

## ۰. اصل بنیادین

> **اپلیکیشن اندروید، همان «یکجا» است — روی همان دیتابیس، همان جداول، همان RLS، همان Storage، همان منطق تجاری. کاربر نباید هیچ فرقی بین تجربه‌ی وب و موبایل حس کند. یک محصول، دو پوسته.**

هیچ دیتابیس دوم، هیچ جدول تازه، و هیچ Policy تازه‌ای ساخته نمی‌شود. تمام معماری این سند حول همین اصل طراحی شده است.

---

## ۱. محدوده‌ی کار

### ۱.۱ چه چیزی ساخته می‌شود
اپلیکیشن اندروید نیتیو (Expo + React Native + TypeScript) با **پوشش ۱۰۰٪ عملکردی و تجربه‌ای** هر ۱۸ صفحه‌ی کاربر نهایی وب‌اپلیکیشن (جدول کامل در بند ۳). خروجی: فایل APK قابل نصب و اشتراک‌گذاری آفلاین (بلوتوث/SHAREit)، از طریق EAS Build.

### ۱.۲ چه چیزی در این فاز نیست
- پنل مدیریت (`/admin/*`) — این پنل، ابزار کار داخلی کارفرماست، نه محصولی که کاربر نهایی می‌بیند؛ مدیریت همچنان از مرورگر (گوشی یا کامپیوتر) انجام می‌شود.
- انتشار در Google Play، پرداخت درون‌برنامه، امتیازدهی، چت داخلی، نوتیفیکیشن Push، نسخه‌ی iOS — این‌ها به‌صراحت در بند ۶.۱۱/۶.۱۴ سند اصلی وب «ویژگی آینده» تعریف شده‌اند، نه بخشی از فاز دوم. معماری این سند مانع افزودن بعدی هیچ‌کدام نمی‌شود.

---

## ۲. معماری کلی — سه لایه، یک مغز

اپلیکیشن موبایل با سرور از دو مسیر داده حرف می‌زند؛ هر دو مسیر روی همان دیتابیس یکسان می‌نشینند:

```
┌─────────────────────────────┐
│      اپلیکیشن اندروید        │
│   (Expo / React Native)     │
└──────────┬───────────┬──────┘
           │           │
   خواندن عمومی    عملیات نیازمند احراز هویت
   (مستقیم)          (از طریق سرور)
           │           │
           ▼           ▼
┌────────────────┐  ┌──────────────────────────┐
│  Supabase       │  │  همان سرور Next.js وب     │
│  (Anon Key)     │  │  /api/mobile/v1/*         │
│  توابع Postgres │  │  (Route Handler ها،       │
│  از قبل آماده   │  │  دقیقاً همان منطق          │
│                 │  │  Server Action های وب)    │
└────────┬────────┘  └────────────┬─────────────┘
         │                        │
         └───────────┬────────────┘
                      ▼
         ┌─────────────────────────┐
         │   یک پایگاه‌داده‌ی واحد    │
         │  Supabase Postgres +     │
         │  PostGIS + Storage +     │
         │  Realtime  (بدون تغییر)  │
         └─────────────────────────┘
```

**مسیر اول (خواندن عمومی):** فهرست/جستجو/جزئیات آگهی‌ها، رانندگان فعال، متخصصین، املاک — مستقیماً از اپ با Anon Key به همان توابع Postgres موجود (`search_listings`, `get_active_drivers`, ...) وصل می‌شود. صفر کد سرور تازه.

**مسیر دوم (نوشتن/احراز هویت):** ثبت آگهی، آپلود عکس، ورود OTP، ویرایش پروفایل، ثبت گزارش. این عملیات‌ها روی وب از طریق Server Action با کوکی امن مرورگر انجام می‌شوند. برای موبایل، **همان منطق دقیق** پشت یک لایه‌ی نازک از Route Handler (`/api/mobile/v1/*`) در همان پروژه‌ی Next.js وب قرار می‌گیرد و با توکن (به‌جای کوکی) شناسایی می‌شود. جزئیات کامل این لایه در بند ۵.

این دو مسیر، یک محصول واحد را می‌سازند: هیچ داده، هیچ Policy، هیچ باکتی که برای وب نباشد، برای موبایل هم وجود ندارد.

## ۳. نگاشت کامل صفحات — تضمین تجربه‌ی یکسان

هر صفحه‌ی کاربر نهایی وب، دقیقاً یک معادل موبایلی دارد. این جدول مرجع الزامی طراحی است — هیچ صفحه نباید حذف، ادغام، یا با تجربه‌ی متفاوت بازسازی شود:

| صفحه‌ی وب (`src/app/[lang]/...`) | صفحه‌ی موبایل معادل | منبع داده |
|---|---|---|
| `/select-language` | صفحه‌ی انتخاب زبان (اولین اجرا) | — (فقط Storage محلی) |
| `/` (خانه) | تب خانه | — (لینک‌های آیکونی به ۴ ماژول) |
| `/auth/login` | صفحه‌ی ورود شماره موبایل | پل موبایل |
| `/auth/verify` | صفحه‌ی تایید کد OTP | پل موبایل |
| `/contact` | صفحه‌ی تماس با ما | — (محتوای ثابت) |
| `/profile` | تب پروفایل / تنظیمات | پل موبایل |
| `/listings` | فهرست/جستجوی کالا | Supabase مستقیم (`search_listings`) |
| `/listings/new` | ویزارد ثبت آگهی کالا | پل موبایل (ثبت) + Storage (آپلود) |
| `/listings/[id]` | جزئیات آگهی کالا | Supabase مستقیم (`get_listing_detail`, `get_similar_listings`) |
| `/transport` | فهرست رانندگان فعال | Supabase مستقیم (`get_active_drivers`) + Realtime |
| `/transport/driver` | فرم پروفایل راننده | پل موبایل |
| `/services` | فهرست/فیلتر متخصصین | Supabase مستقیم (`get_active_service_providers`) |
| `/services/provider` | فرم پروفایل متخصص | پل موبایل |
| `/real-estate` | فهرست/جستجوی املاک | Supabase مستقیم (`search_real_estate`) |
| `/real-estate/new` | ویزارد ثبت آگهی ملک | پل موبایل + Storage |
| `/real-estate/[id]` | جزئیات آگهی ملک | Supabase مستقیم (`get_real_estate_detail`, `get_similar_real_estate`) |
| `/report/new` | فرم ثبت گزارش تخلف | پل موبایل |
| `/users/[id]` | پروفایل عمومی کاربر | پل موبایل |

جمعاً **۱۸ صفحه** — همه در فازهای M00B تا M06 پوشش داده شده‌اند (سند فازها). صفحات `/admin/*` عمداً از این جدول حذف شده‌اند (بند ۱.۲).

## ۴. پشته‌ی فناوری

| لایه | تکنولوژی |
|---|---|
| فریم‌ورک | Expo (Managed Workflow) + React Native + TypeScript (Strict) |
| ناوبری | Expo Router (مسیریابی فایل‌محور). زبان به‌صورت Context سراسری مدیریت می‌شود، نه به‌عنوان بخشی از مسیر (بدون پوشه‌ی `[lang]`) — چون در اپ موبایل، برخلاف وب، مسیر قابل اشتراک‌گذاری/SEO معنا ندارد؛ این یک ساده‌سازی عمدی نسبت به معماری وب است. |
| استایل | React Native StyleSheet + یک فایل توکن مرکزی `constants/theme.ts` (همان مقادیر رنگی دقیق وب: `#06b6d4`/`#f97316`/... + فونت Vazirmatn) |
| کلاینت داده | `@supabase/supabase-js` (همان پروژه‌ی Supabase وب، فقط Anon Key) |
| نشست | `expo-secure-store` (معادل native کوکی httpOnly) |
| موقعیت مکانی | `expo-location` |
| عکس | `expo-image-picker` + `expo-image-manipulator` (همان هدف فشرده‌سازی وب: ~۱۵۰-۲۵۰ کیلوبایت، حداکثر ۱۲۸۰ پیکسل) |
| Build | EAS Build (پروفایل APK) |

**دو تصمیم اجرایی نهایی‌شده (نسخه‌ی ۲.۰):**
1. به‌جای NativeWind، از React Native StyleSheet ساده + یک فایل توکن مرکزی استفاده می‌شود — چون نصب/نگهداری NativeWind لایه‌ی پیکربندی اضافه (Babel/Metro/PostCSS) با ریسک شکنندگی بین نسخه‌ها دارد، و همان هدف (رنگ/فونت برند یکسان) با راه ساده‌تر و پایدارتر کاملاً محقق می‌شود.
2. زبان به‌جای پوشه‌ی مسیر `[lang]`، یک Context سراسری است — چون در اپ موبایل نیازی به URL قابل اشتراک به هر زبان نیست.

## ۵. معماری ارتباط با سرور — لایه‌ی API موبایل (`/api/mobile/v1/*`)

این تنها بخشی از فاز دوم است که در **ریپازیتوری وب موجود** (نه در پروژه‌ی Expo) نوشته می‌شود — چون منطق تجاری (ثبت آگهی، بررسی مالکیت، آپلود امن) از قبل آنجا نوشته و تست شده و نباید در جای دوم بازنویسی شود. این لایه هیچ تصمیم امنیتی یا محصولی تازه نمی‌گیرد؛ فقط همان مسیر Server Action موجود را در قالب یک Route شناخته‌شده برای HTTP در دسترس اپ می‌گذارد:

| Route | معادل Server Action وب | خروجی |
|---|---|---|
| `POST /api/mobile/v1/auth/request-otp` | `sendOtp` (فاز ۰۱) | تایید ارسال |
| `POST /api/mobile/v1/auth/verify-otp` | `verifyOtpAction` | توکن نشست (JSON) |
| `GET/PATCH /api/mobile/v1/profile` | `profile/actions.ts` | پروفایل / تغییر زبان |
| `POST /api/mobile/v1/marketplace/listings` | `listings/new/actions.ts` | آگهی ثبت‌شده |
| `POST /api/mobile/v1/marketplace/upload-slots` | `createSignedUploadSlotsAction` | Signed URL |
| `POST/PATCH /api/mobile/v1/transport/driver` | `transport/driver/actions.ts` | پروفایل راننده |
| `PATCH /api/mobile/v1/transport/driver/location` | همان (تسک به‌روزرسانی موقعیت) | تایید |
| `POST/PATCH /api/mobile/v1/services/provider` | `services/provider/actions.ts` | پروفایل متخصص |
| `POST /api/mobile/v1/real-estate/listings` | `real-estate/new/actions.ts` | آگهی ثبت‌شده |
| `POST /api/mobile/v1/reports` | `report/new/actions.ts` | تایید ثبت |
| `GET /api/mobile/v1/users/:id` | معادل `getPublicUserProfile` | پروفایل عمومی |

**مکانیزم نشست:** توکن امضاشده با همان الگوریتم HMAC-SHA256 و همان `SESSION_SECRET` که وب استفاده می‌کند — فقط به‌جای `Set-Cookie`، در بدنه‌ی JSON پاسخ برمی‌گردد. اپ آن را در `expo-secure-store` نگه می‌دارد و در هدر `Authorization: Bearer <token>` هر درخواست بعدی می‌فرستد. تابع `requireUser()`/`requireAdmin()` موجود در `src/lib/auth/session.ts` یک شاخه‌ی کوچک اضافه می‌کند: کوکی را چک کند، نبود، از هدر بخواند. همین.

**سطح دسترسی:** هیچ کلید Service Role هرگز به اپ موبایل نمی‌رسد. اپ فقط Anon Key (خواندن عمومی) و توکن نشست خودش را دارد — دقیقاً هم‌سطح امنیتی مرورگر وب، نه بیشتر و نه کمتر.

## ۶. یکپارچگی زبان و برند (بدون هیچ واگرایی از وب)

- فایل‌های `fa.ts`/`ps.ts` (دیکشنری) و تمام فایل‌های تک‌نقطه‌ی حقیقت (`categories.ts`, `vehicleTypes.ts`, `propertyTypes.ts`, `dealTypes.ts`, `reasons.ts`, `reportTargets.ts`, `phone.ts`) — همگی فایل TypeScript خالص و مستقل از Next.js — عیناً کپی می‌شوند. صفر بازنویسی، صفر ریسک ناهماهنگی مقادیر با CHECK constraint های دیتابیس.
- هویت بصری (رنگ، فونت Vazirmatn، آیکون‌های دسته‌بندی) عیناً از وب گرفته و در `constants/theme.ts` (یک فایل توکن مرکزی React Native StyleSheet) پیاده می‌شود — نه یک کتابخانه‌ی استایل‌دهی تازه.
- ناوبری پایین صفحه (۵ آیتم: خانه/آگهی‌ها/حمل‌ونقل/خدمات/پروفایل) — همان معماری اطلاعاتی PWA وب، این‌بار native.
- مودال سلب مسئولیت معامله‌ی خارج از اپ، دقیقاً با همان متن و همان منطق نمایش یک‌باره.

---

## ۷. بهینه‌سازی برای اینترنت ضعیف و گوشی‌های رده‌پایین

معیارهای بند ۶.۱۲ سند اصلی وب (سرعت روی ۲G/۳G، سبک بودن، حداقل درخواست شبکه) عیناً برای موبایل هم الزامی‌اند:
- فشرده‌سازی تصویر پیش از آپلود (بند ۴ سند فناوری).
- هر صفحه با یک فراخوانی تابع Postgres (نه چند کوئری جدا) داده‌ی کامل خودش را می‌گیرد — دقیقاً معماری وب.
- کش محلی آخرین نتایج برای نمایش فوری در باز شدن مجدد اپ (جزئیات در فاز M07).

---

## ۸. معیار پذیرش نهایی فاز دوم

فاز دوم زمانی تمام است که:
- هر ۱۸ صفحه‌ی بند ۳، با تجربه‌ی کاربری یکسان با وب، در اپ کار کند.
- هیچ تفاوت محسوسی (چیدمان، رنگ، متن، سرعت) بین تجربه‌ی وب و موبایل برای کاربر نهایی وجود نداشته باشد.
- جریان OTP، آپلود عکس، و ثبت گزارش از طریق پل موبایل کامل کار کند.
- تست روی گوشی رده‌پایین و اینترنت ضعیف با موفقیت انجام شود.
- APK از طریق EAS Build ساخته و آفلاین قابل اشتراک‌گذاری باشد.

## ۹. جمع‌بندی

معماری این فاز طوری طراحی شده که کل تیم موبایل، تقریباً تمام وقتش را صرف طراحی و ساخت تجربه‌ی native کند؛ تنها قطعه‌ی مهندسی سمت سرور (بند ۵) کاری مکانیکی و کاملاً مشخص‌شده است — بدون ابهام، بدون تصمیم باز. جزئیات اجرایی گام‌به‌گام در `YAKJA_MOBILE_PHASES_ROADMAP.md` و ساختار کامل دیتابیس در `YAKJA_DATABASE_LOG.md` آمده است.
